同比、环比、占比、基期比较

指标公式注意
同比增长率(本期 − 去年同期) ÷ 去年同期对齐相同时段和统计口径。
环比增长率(本期 − 上期) ÷ 上期上期是紧邻的统计周期。
总额占比本组金额 ÷ 全部金额分母不是另一个单独分组。
相对基准百分比当前地区金额 ÷ 基准地区金额基准地区自身为 100%。
相对基准差额当前地区金额 − 基准地区金额基准地区自身为 0。

基期为 0 时不能直接相除。同比与环比只能说明变化，不能单独证明店长、产品经理或某次活动的效果。

典型题：思路、写法与答案

题 1：9 月销售额 120，8 月 100，去年 9 月 80。同比、环比各是多少？

思路：分别找“去年同期”和“上期”，不要把两个基数混用。

答案与检查：同比 = (120−80)÷80 = 50%；环比 = (120−100)÷100 = 20%。

题 2：某地区男性 200、女性 300，男性在该地区占多少？

思路：分母取该地区合计，而不是全国男性合计。

答案与检查：200 ÷ (200+300) = 40%。地区在行、性别在列时选行汇总百分比。

题 3：增加新月份记录后，透视表总额没变，怎样排查？

思路：从源数据、范围、刷新、筛选四处检查。

答案与检查：确认记录已加入数据源；检查超级表是否扩展；刷新透视表；检查日期分组和切片器是否仍排除了新月份。

插入数据的四种写法

写法是否写列名单行 / 多行
INSERT INTO 表(列...) VALUES(...)写单行；推荐显式列名。
INSERT INTO 表 VALUES(...)不写单行；必须符合完整列顺序。
INSERT INTO 表 VALUES(...),(...)不写多行；每行数量和顺序要正确。
INSERT INTO 表(列...) VALUES(...),(...)写多行；更利于维护。

MySQL 的 INSERT 可使用 VALUE 或 VALUES；推荐统一用 VALUES。字符串和日期通常用单引号。非空且无默认值的普通字段需要提供；自增列通常可省略。

修改、删除与事务区别

命令作用注意
UPDATE … SET … WHERE …修改满足条件的记录没有 WHERE 会更新全表；重复调薪会重复增加。
DELETE FROM … WHERE …删除满足条件的记录InnoDB 中能否回滚取决于事务是否尚未提交。
TRUNCATE TABLE …清空整表，通常重置自增MySQL 中会隐式提交，不能当作普通可回滚删除。
DROP TABLE …删除表结构与数据与清空记录不同。

电商项目：15 项需求与完整 SQL

01 · 各渠道订单量

思路：按渠道分组，对已有订单数量字段求和。

SELECT chann_name,SUM(order_num) AS order_count
FROM dw_data GROUP BY chann_name;

答案与检查：每个渠道一行。若原表是一行一单的明细，需按实际粒度判断 COUNT 或去重订单号，而不是机械 SUM。

02 · 各地区实付金额

思路：按地区分组，对 real_money 求和。

SELECT address,SUM(real_money) AS paid_amount
FROM dw_data GROUP BY address;

答案与检查：各地区金额合计应与同一数据范围的总实付金额一致。

03 · 各地区、各渠道实付金额

思路：同时保留地区和渠道两个维度，先输出可复用的长表。

SELECT address,chann_name,SUM(real_money) AS paid_amount
FROM dw_data
GROUP BY address,chann_name;

答案与检查：地区与渠道的每种组合一行，方便 BI 筛选与转交叉表。

04 · 各渠道最大消费金额

思路：按渠道分组，使用 MAX 而不是 SUM。

SELECT chann_name,MAX(consume_money) AS max_consume
FROM dw_data GROUP BY chann_name;

答案与检查：MAX 得到最大单条记录的消费金额；若原表不是单笔消费粒度，先明确“最大单笔”的聚合单位。

05 · 各地区实付金额占比

思路：地区合计作为分子，同范围全部金额作为分母。

SELECT part.address,part.amount,
 ROUND(100.0*part.amount/NULLIF(total.amount,0),2) AS ratio_pct
FROM (
 SELECT address,SUM(real_money) AS amount
 FROM dw_data GROUP BY address
) part
CROSS JOIN (SELECT SUM(real_money) AS amount FROM dw_data) total;

答案与检查：ratio_pct 为百分数数值；四舍五入前合计应为 100%，舍入后允许小幅差异。

06 · 各地区内部男女实付金额占比

思路：按地区、性别求和，再除以同地区总额。

SELECT d.address,d.sex,
 ROUND(100.0*SUM(d.real_money)/NULLIF(region.amount,0),2) AS ratio_pct
FROM dw_data d
JOIN (
 SELECT address,SUM(real_money) AS amount
 FROM dw_data GROUP BY address
) region ON d.address=region.address
GROUP BY d.address,d.sex,region.amount;

答案与检查：同一地区各性别占比合计约 100%；这个分母与“同一性别在各地区如何分布”不同。

07 · 以东北为基准的金额百分比

思路：当前地区总额除以东北总额，不是除以全部地区总额。

SELECT part.address,
 ROUND(100.0*part.amount/NULLIF(base.amount,0),2) AS ratio_pct
FROM (
 SELECT address,SUM(real_money) AS amount
 FROM dw_data GROUP BY address
) part
CROSS JOIN (
 SELECT SUM(real_money) AS amount FROM dw_data WHERE address='东北'
) base;

答案与检查：若保留东北行，其值应为 100%。东北金额为 0 或缺失时返回 NULL；只要其余地区可再过滤东北行。

08 · 与东北实付金额的差额

思路：地区总额减东北总额，保留正负号。

SELECT part.address,part.amount-base.amount AS amount_diff
FROM (
 SELECT address,SUM(real_money) AS amount
 FROM dw_data GROUP BY address
) part
CROSS JOIN (
 SELECT SUM(real_money) AS amount FROM dw_data WHERE address='东北'
) base;

答案与检查：东北自身为 0；正数表示高于东北，负数表示低于东北。

09 · 2017–2020 年度增长率

思路：先按年汇总，再连接上一年；只比较相邻年份。

WITH yearly AS (
 SELECT YEAR(create_time) AS yr,SUM(real_money) AS amount
 FROM dw_data GROUP BY YEAR(create_time)
)
SELECT cur.yr,cur.amount,
 ROUND(100.0*(cur.amount-prev.amount)/NULLIF(prev.amount,0),2) AS growth_pct
FROM yearly cur
LEFT JOIN yearly prev ON prev.yr=cur.yr-1
WHERE cur.yr BETWEEN 2017 AND 2020
ORDER BY cur.yr;

答案与检查：这里是年度同比增长。没有上年记录或上年金额为 0 时为 NULL；CTE 写法要求 MySQL 8。

10 · 各地区实付金额累计

思路：先规定六个地区的顺序，再把当前及以前地区的金额相加。

WITH region_totals AS (
 SELECT address,SUM(real_money) AS amount,
  FIELD(address,'西北','华北','东北','华东','中南','西南') AS seq
 FROM dw_data GROUP BY address
)
SELECT cur.address,cur.amount,SUM(prior.amount) AS running_amount
FROM region_totals cur
JOIN region_totals prior ON prior.seq<=cur.seq
GROUP BY cur.address,cur.amount,cur.seq
ORDER BY cur.seq;

答案与检查：本例沿用六地区列表；其他地区须先明确归类。最后一个地区的累计额应等于总额。CTE 要求 MySQL 8。

11 · 各地区消费金额按名称排序

思路：先求和，再按约定的名称排序规则展示。

SELECT address,SUM(consume_money) AS consume_amount
FROM dw_data GROUP BY address
ORDER BY CONVERT(address USING gbk);

答案与检查：笔记用转 GBK 的写法做中文排序练习；字符编码顺序不等于所有场景下通用的拼音顺序，结果需核对。

12 · 各地区独立用户数，并自定义顺序

思路：明确人数应去重，再用 FIELD 指定六地区顺序。

SELECT address,COUNT(DISTINCT user_id) AS user_count
FROM dw_data GROUP BY address
ORDER BY FIELD(address,'西北','华北','东北','华东','中南','西南');

答案与检查：同一个人在同一地区出现多次只算一人；跨地区去重人数不可简单相加。FIELD 对未列出的地区返回 0，新增地区要处理。

13 · 各年各季度实付金额

思路：同时用年份和季度分组，避免把不同年份同季度混到一起。

SELECT YEAR(create_time) AS yr,QUARTER(create_time) AS qtr,
 SUM(real_money) AS paid_amount
FROM dw_data
GROUP BY YEAR(create_time),QUARTER(create_time)
ORDER BY yr,qtr;

答案与检查：输出年、季度、金额；按年再按季度升序。

14 · 各年龄段实付金额

思路：用 CASE 覆盖五个区间，显式保留范围外与缺失年龄。

SELECT CASE
 WHEN age BETWEEN 18 AND 27 THEN '18-27'
 WHEN age BETWEEN 28 AND 37 THEN '28-37'
 WHEN age BETWEEN 38 AND 47 THEN '38-47'
 WHEN age BETWEEN 48 AND 57 THEN '48-57'
 WHEN age BETWEEN 58 AND 67 THEN '58-67'
 ELSE '其他/未知' END AS age_group,
 SUM(real_money) AS paid_amount
FROM dw_data
GROUP BY age_group
ORDER BY FIELD(age_group,'18-27','28-37','38-47','48-57','58-67','其他/未知');

答案与检查：18–27、28–37 等边界包含两端；其他年龄和 NULL 进入“其他/未知”，避免漏掉金额。

15 · 各渠道金额，并支持按性别筛选

思路：汇总时保留 sex，按渠道与性别两个维度分组。

SELECT chann_name,sex,SUM(real_money) AS paid_amount
FROM dw_data
GROUP BY chann_name,sex;

答案与检查：结果交给 FineBI，用 sex 做筛选。若汇总只保留渠道，则后续不能恢复性别维度。

易错对照

容易混的点正确理解
记录数 / 用户数COUNT(user_id) 数记录；COUNT(DISTINCT user_id) 数独立用户。
按性别筛选汇总时必须保留 sex 维度，否则 BI 无法恢复。
金额占比 / 金额差额占比先找分母；差额直接相减；分母为 0 要处理。

不能。需要重新按渠道、性别分组，并在结果中保留 sex。

2. 先确认三个统计口径

  • 订单量：已有汇总数量用 SUM(order_num)；按订单明细统计时确认是否要去重。
  • 用户数：COUNT(user_id) 是记录计数；独立用户数通常用 COUNT(DISTINCT user_id)。

3. 三种可复用 SQL

-- 各渠道订单量
SELECT chann_name, SUM(order_num) AS order_count
FROM dw_data
GROUP BY chann_name;
-- 每个地区内部，男女实付金额占比
SELECT d.address, d.sex,
  ROUND(100.0 * SUM(d.real_money)
        / NULLIF(t.region_money, 0), 2) AS ratio_pct
FROM dw_data d
JOIN (
  SELECT address, SUM(real_money) AS region_money
  FROM dw_data
  GROUP BY address
) t ON d.address = t.address
GROUP BY d.address, d.sex, t.region_money;
-- MySQL 8：每年与上一年相比的金额增长率
WITH yearly AS (
  SELECT YEAR(create_time) AS yr, SUM(real_money) AS money
  FROM dw_data
  GROUP BY YEAR(create_time)
)
SELECT cur.yr,
  ROUND(100.0 * (cur.money - prev.money)
        / NULLIF(prev.money, 0), 2) AS growth_pct
FROM yearly cur
LEFT JOIN yearly prev ON prev.yr = cur.yr - 1
WHERE cur.yr BETWEEN 2017 AND 2020
ORDER BY cur.yr;

补充：NULLIF 防止分母为 0；没有上一年记录时增长率为 NULL。年度对上年度应称年度同比增长，不是月度环比。以上示例假设地区非空，空地区应在清洗时明确归类。

              理论
                数据类型本身就是一种约束，数据约束是指在数据类型限定的基础上额外增加的要求
              常用约束
                主键 primary key
                  唯一标识表中的一行记录。 MySQL 建议所有表的主键字段都叫 id， 类型为int
                主键自增auto_increment
                  设置主键自增之后，新增数据时，数据库会自动把id值加1
                非空 not null
                  此字段不允许填写空值。NULL表示空
                唯一 unique
                  此字段不能重复
                默认 default
                  不填写字段对应的值会使用默认值，如果填写时以填写为准
                  格式
                    default 值
                      如果值是文字需要使用引号包裹
            COMMENT
              可以对字段做出备注，方便知道字段的含义
              注意
                备注内容需要被引号包裹
                  例如：comment='字段名称'
            注意

数据分析DAY08
  分层
    数据仓库架构可分为三层
      源数据层(ODS)
        直接把外部系统的数据原样搬过来，不改字段、不改内容，不对外给别人用
        就是一块临时存放接口原始数据的地方，给后面的数据加工做准备
      数据仓库层(DW)
        把 ODS 的原始数据清洗干净，去掉脏数据，得到统一、准确的数据
      数据应用层(DA或ADS层)
        给前端程序直接读的数据，按报表、专题分析的要求加工计算出来
    思考
      为什么需要有这样的三层架构,不直接存在一张表内呢
        分层是分步处理数据，原始数据、清洗明细、报表数据分开存放，互不影响，查询更快、方便排查问题
